Minimum runtime query/index cure, once installation is safely admitted:
1. Preserve the primary key, owner index, all terminal rows, all visibility
   checks and all quota quantities. Add an index on (room_id,state).
2. Add state IN ('staged','committed') to quota's WHERE clause. Keep the
   per-uploader staged/byte conditions and existing expiry-before-quota
   transaction order. Index alone or predicate alone leaves quota at 20,192
   reads in this fixture. Together: quota195, list387, expiry65.
3. Do not delete tombstones or place a lifetime-record cap on them: their
   retained IDs provide conflict/idempotency and privacy behavior, while
   the existing 4096-record quota intentionally counts only live rows.

Partial-index alternatives were measured, not proposed as an automatic
constructor fix. A partial (room_id,state) WHERE live index requires an
explicit matching live predicate on expire() as well; the original expiry
query does not select it. With that extra predicate expiry reads196 here.
A partial (room_id,created_at DESC,id) WHERE live index removes list sorting;
live-filtered quota reads192 and live-filtered expiry reads193. It keeps
only live entries but has broader ordering/key considerations.

Pagination: under existing/room-state indexes, LIMIT20 and LIMIT20 OFFSET100
still read20384/387 respectively, the same as their full lists. The ordered
partial index reads20 for first page and120 for OFFSET100. Current API has
no pagination contract and applies DM/uploader visibility after SQL: adding
LIMIT before visibility can return an apparently empty/incomplete page
despite later visible files. A future cursor must preserve order and privacy;
pagination is not needed to implement the minimum live-row selection cure.
The current live-record cap bounds the normal full list to4096, but does not
bound its historical scan or global index installation.

Before index construction, an explicit operator action must independently
admit the complete database-wide attachment input: a bounded count+1 scan
over the existing primary-key order, scalar/type checks and byte limits on
every index key (room_id/state, plus created_at/id for an ordered variant),
including tombstones and every room. Refuse over-budget inputs before DDL.
The admitted bytes/count and schema/index identity must remain bound to
execution under the same writer transaction; index creation must have a
qualified worst-case budget and atomic rollback. A per-room bound or a
LIMIT in the runtime query cannot admit this global operation. No arbitrary
new thresholds have been selected or justified by this fixture.

No existing operator tool with that global row/key-byte admission was found:
operator-message-authority and legacy repair admit per-room message inputs;
operator archive bounds message replay; scripts/schema-gate is a CI harness;
scripts/herdr-migrate handles claim migration. None is an attachment-index
installation door. Thus this is a concrete residual migration prerequisite,
not a request to create a new subsystem in the current wave.

Schema convergence details: server/attachment-schema.mjs:30 returns early
for an already-current table. Appending index DDL alone will not install it
on those databases. ensureAttachmentSchema@1 participates in the deferred
startup schema stamp (server/store.mjs ADDITIVE_SCHEMA_ENSURES). Updating
the helper/stamp to build the index on the next constructor would silently
move the global scan onto a request's cold start. Keep installation explicit;
only after admitted execution should schema/index verification recognize
the intended index and reject a conflicting definition. The existing v28
table-rebuild migration must continue preserving rows/bytes and old lineage.
