Source and authority
server/mcp-oauth.mjs:60–92,126–157: account-agent is a current sponsored identity/member bound to one room, not account-wide creation authority. The supported scopes contain no rooms:create. server/mcp-room-profile.mjs:1016–1043 filters discovery/dispatch and forces the approved room. Its room_create implementation at530–536 calls AgentRooms.create and grants agent ownership, not human ownership.
server/room-lifecycle.mjs:123–174 authenticates an actual account session, applies existing creation/email/administration/capacity rules, creates the human owner and binds that account. server/http.mjs:2582–2591 adds cookie/session-binding/CSRF protections.
server/agent-identities.mjs:1301–1341 requires the existing holder secret and an already existing target room to mint a single-use target-bound link code. AgentConnections.apply requires that proof plus signed-in account authority (server/agent-connections.mjs:165–220,278–290). A sponsor's account cannot mint holder proof merely from the identity ID. Native MCP OAuth bearer is deliberately not a REST or global identity secret.
Current positive composition therefore exists only when the actual identity holder can supply that existing proof. A native-only host normally holds only its opaque room-bound OAuth tokens, not pri_. Exposing pri_ in a browser URL, copying a label/provider subject, reinterpreting OAuth userId as a human session, or internally issuing a proof on behalf of the holder would violate present authority. Do not implement those shortcuts.

First choice: find an existing suitable human-owned room
Keep existing owned-room discovery before create. The contextual signed-in browser can use GET /api/account-rooms, then select an already authorized room/agent binding through the existing native account OAuth screen. The native token cannot silently list all account rooms. This selection is setup consent, not mandatory routine Room visits. Do not create another sovereign room just because the primary interface is an agent. If a suitable human-owned room and target-native connection already exist, no creation extension is needed.

Smallest safe orchestration with existing holder proof
A narrow contextual browser page (not a new dashboard) uses existing account session/sign-in and CSRF. It presents room title/purpose/ownership, the exact selected existing identity, permission preset and expiry. After explicit create approval it calls existing POST /api/account-rooms with stable roomId/spec. Only once that room exists may the holder mint existing target/sponsor-bound link proof using its existing authenticated identity client. Proof travels in authenticated POST bodies, never a URL or chat log. Human approval of the exact agent connection then invokes the existing agent-connections create and normal target-room OAuth selection. Existing room and invitation paths remain unchanged.
No new user password/login/key is necessary. This is not currently a complete native-only flow: the preferred native agent cannot produce the required holder proof through its present room-bound OAuth connection. Also, ordinary target OAuth authorization necessarily issues normal provider tokens; “no new credentials” can mean no new user-managed secret or credential system, not literally no normal token issuance. Existing connection create also requires its normal target credential digest. Do not hide this distinction.

Proposed emitted handoff contract (before runtime implementation)
version1, type human_owned_room_setup, stable requestId, exact canonical origin/resource, requested roomId/title/purpose/kind, ownership human_account, explicit source account-agent descriptor (familyId/resource/roomId/identityId/memberId/scopes; no access/refresh/identity secret), selected access preset and bounded expiry, status proposal|approval_required|holder_proof_required|created|target_oauth_required|ready|refused, exact next step, receipt reference when committed. All proposal text is untrusted until the browser authenticates and re-resolves the selected account/agent. Browser state uses account session, session binding and CSRF; the account must match the current source sponsorship. A handoff URL contains only a proposal/intent reference; it is not authority to create, link, inspect or recover the room. No raw proof/token in URLs. Current emitted example correctly reports holder_proof_required rather than inventing a working approval link.

If native-only creation is required: exact new authority needing root review
Existing authority cannot complete it. The smallest new contract is one request-bound, explicit human setup consent to enroll THIS presently sponsored native identity in THIS new human-owned room, with THIS preset/expiry. It is not an account-wide OAuth scope, not a new auth system and not automatic cross-room access for existing grants. Human account authentication and exact original native principal must both be revalidated at commit. Approval must explicitly state it is the authority for this target enrollment; do not claim it is the old target-bound holder code. Root must decide whether this new authority is acceptable, since current per-room holder-proof policy does not already allow it.
Use a bounded, expiring room-setup intent/receipt only if this new authority is approved. It records request fingerprint, account, original native family/identity epoch/source connection, exact target spec/permissions/expiry, approval and commit receipt. Metadata only, no identity secret or task/result contents. One intent is not a bearer credential, membership or background execution grant. Do not force it into oauth_pending_states (provider CHECK permits only google/github, and it stores provider session/verifier fields), or oauth_invite_pending (its semantics are invitation consumption/new-seat grants). Reusing those tables without a reviewed schema/retention/export/fence contract would be a hidden parallel authorization system. A new bounded purpose-specific receipt is more honest than misusing them; no implementation is authorized yet.
