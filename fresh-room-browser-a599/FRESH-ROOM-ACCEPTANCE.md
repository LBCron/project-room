## Acceptance that applies to either product choice

1. A newly created account room and a newly created agent room must have a truthful current capability response. An unsupported aggregate must not be fabricated as empty/working. Preserve bounded reads, private definitions and session/viewer binding.
2. A fresh human owner can discover the Room assistant's state in Settings at desktop1280 and phone390. If supported, setup must be reachable and honor current membership authority. If unsupported, a visible explanation must state that limitation and provide a useful current next step. A silently missing row is not a verified discoverable state.
3. Sending an explicit @Room question must preserve the posted text and avoid implying assistant execution without a recorded request/host observation. When invocation is unavailable, the UI must provide a visible, accessible explanation; ordinary conversation with other members remains usable.
4. Updates and Catch-up must either show valid current data or explain the unavailable scope with a real supported destination. Do not interpret omitted work/notification/run aggregates as zero activity.
5. Reload preserves the same room and conversation, with the same capability explanation. Switching to a legacy/supported room must restore its applicable controls; no cached unavailable flag may cross room/session boundaries.
6. No automatic provider/model invocation, execution grant, background schedule, destructive migration or legacy fallback follows from displaying a setup/explanation affordance.
